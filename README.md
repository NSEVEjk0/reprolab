# ReproLab

Reproduce a bug, contain an AI repair, and take away evidence you can replay. A fresh gVisor sandbox runs each candidate; the expected answers and acceptance decision stay in a separate controller.

ReproLab starts with three small, owned Python failures: month-end scheduling, checkout rounding and webhook retries. Each has 20 independent cases. A live job first demonstrates the original failure, asks **Vultr Serverless Inference** for a repair, then checks it in another disposable sandbox. One failed repair can receive one bounded retry.

## Use the lab

Open the [public ReproLab preview](https://reprolab-ckay.vercel.app) to inspect the executed reference repairs and their evidence. The live Vultr controller and inference connection remain to be configured.

Choose a failure, start a live repair and inspect the original failures, candidate results, exact source and image fingerprints, and confirmed removal of each sandbox. Download the evidence and replay the candidate yourself.

The browser also supports **explicitly labelled reference examples** generated by real sandbox execution in CI. Reference patches are disclosed fixtures, not AI-generated repairs. Missing inference credentials return 503; the live API never falls back to a reference patch.

## Run and verify

Use Python 3.12+ on a dedicated Linux x86_64 Docker host. Install the pinned gVisor release and image using `bash infra/install-gvisor.sh`; this changes the Docker runtime configuration on that host. No generated code runs through ordinary Python on the host.

```sh
python3 -m reprolab.cli doctor
python3 -m unittest tests.test_unit -v
REPROLAB_INTEGRATION=true python3 -m unittest tests.test_integration -v
python3 -m reprolab.cli run month-end --output evidence.json
python3 -m reprolab.cli verify evidence.json
python3 -m reprolab.cli replay evidence.json
```

`run` requires `VULTR_INFERENCE_API_KEY`. A successful job records `status: verified`, a reproduced baseline failure, a passing independent evaluation and confirmed teardown. `verify` checks integrity, source binding, case fingerprints and the recorded sandbox policy. `replay` executes the saved candidate in a new pinned gVisor sandbox and compares it against the recorded cases.

For a model-free infrastructure test, explicitly request a reference evaluation:

```sh
python3 -m reprolab.cli reference rounding --output reference.json
python3 -m reprolab.cli verify reference.json
python3 -m reprolab.cli probes --output containment.json
```

The probe uses a controller-owned dummy file. It checks host-file and network isolation, nonroot execution, read-only mounts, execution timeout, streaming output limits and teardown. Adversarial integration tests reject `sys.exit(0)` and fake success banners.

## Deploy on Vultr

The contest deployment needs **both this web interface and its controller on Vultr**, and live repairs must use Vultr Serverless Inference. A static frontend preview elsewhere is not that deployment.

On a dedicated Ubuntu 24.04 VM:

1. Install Docker, Python, Caddy and the pinned gVisor runtime. Pull the immutable Python image.
2. Put this repository in `/opt/reprolab`. Create a `reprolab` service user and `/var/lib/reprolab` state directory. The service user's Docker access is part of the trusted controller boundary.
3. Store `.env.example` values privately in `/etc/reprolab/reprolab.env`, readable only by root. Use the actual HTTPS origin, a Vultr inference key and either a demo access code or an explicit `REPROLAB_PUBLIC_JOBS=true` setting. The default permits no live jobs.
4. Install the controller and garbage-collection service/timer from `infra/`. Point a domain to the VM, configure Caddy from the example and enable the services.
5. Run `doctor`, the integration tests, a real inference repair and a local replay. Inspect the browser and the downloaded evidence before recording a demo.

The controller serves the interface and `/api/*` together. It accepts only supported fixture IDs, has a four-job queue, one repair worker and an atomic daily budget (default eight jobs). Each job is read using an unguessable capability token; only its hash is stored. A restart marks pending jobs interrupted and starts no automatic paid retries. An independent timer removes expired containers owned by that deployment.

## Execution boundary

Every candidate uses `--runtime=runsc`, an immutable image digest, no network, a read-only root and work mount, UID 65532, dropped capabilities and `no-new-privileges`. Budgets are 192 MiB, 0.5 CPU, 48 PIDs, 16 MiB temporary storage, eight seconds and 64 KiB combined stdout/stderr. Output is bounded **while streaming**, not after capture. Docker control commands are bounded too. There is no silent `runc` fallback.

The sandbox sees input cases and a fresh nonce. It never receives the expected-output table or provider credentials. The outside evaluator requires the exact result protocol, checks typed JSON results and rejects stale, incomplete or malformed responses. A passing exit code alone cannot pass a repair.

Teardown always attempts to remove the exact owned container and queries the daemon for its absence. Daemon failure is recorded as **teardown unconfirmed** and cannot produce a verified repair. Cleanup after a hard controller failure relies on the independent watchdog or subsequent startup; no instant destruction guarantee is claimed.

## Evidence and limits

Schema v2 includes the parsed payload, its canonical UTF-8 bytes and their SHA-256. Keeping the original canonical bytes makes browser verification and downloads preserve numeric representations. Fingerprints detect changes and bind the replay inputs and source. **They do not attest the host, controller or inference provider.** A trusted operator and Docker daemon remain required, and gVisor is a software isolation layer rather than a TEE or a separate microVM kernel.

Passing 20 cases is finite test evidence, not proof for every input. The current app supports the three maintained fixtures rather than arbitrary uploaded repositories. Only their source, known example and observed failure are sent to Vultr inference. The remaining input cases and expected answers stay in the controller/evaluator path. No provider key enters a candidate container.
